## 引言

[[freertos-semaphore-callback|信号量一篇]]讲了任务间怎么"打招呼"，但打招呼只能同步、不能带话——采集任务采到一组 ADC 值要交给处理任务，光 give 一个信号量不够，数据怎么过去？全局变量加锁当然行，但 FreeRTOS 有更体面的答案：**队列**，把数据本身拷进一个线程安全的管道。

这页笔记讲三件进阶的事：队列的拷贝语义与阻塞行为、任务通知这条不走中介的直达路线、以及互斥锁背后的优先级反转与优先级继承——最后这块在信号量一篇里只有一句话，这里把时间线彻底拆开。

## 一、队列：会拷贝数据的管道

![[frtos-queue-sequence.webp|队列读写时序（Mastering FreeRTOS Figure 31）：Task A 两次发送把 10、20 拷贝进队列，Task B 稍后按先进先出依次取出——数据经队列以副本传递，发送方发完即与接收方解耦]]

先立住最核心的语义：**队列传的是值的拷贝，不是引用**。发送时数据被 memcpy 进队列内部存储，接收时再拷出来。发送方发完立刻可以复用甚至销毁那个变量，两边的生命周期被队列彻底解耦。传指针当然也允许——把指针当"值"拷进去——但指向的内存谁释放、会不会被发送方改掉，全成了约定俗成的隐患；默认拷贝换的是安心，结构体小就别耍聪明。

时序图里 Task A 把 10、20 两次送进队列，Task B 按先送先进的顺序取走，Task A 发完继续跑自己的，不必知道对方何时取。围绕这个 FIFO，阻塞行为有四条规则：

| 场景 | 行为 |
| --- | --- |
| 队列满时发送 | 带阻塞时间的发送方进阻塞态等空位；超时返回 errQUEUE_FULL |
| 队列空时接收 | 接收方阻塞等数据——"消费者睡觉，来货再叫醒" |
| 多个任务等同一队列 | 按优先级唤醒，同级先来先服务 |
| 中断里收发 | 不允许阻塞，FromISR 版本失败直接返回，靠返回值善后 |

最小骨架，采集任务到处理任务的单向数据流：

```c
QueueHandle_t xQueue = xQueueCreate(5, sizeof(int16_t)); // 5 格，每格 2 字节

// ---- 生产者任务 ----
int16_t sample = ADC_Read();
xQueueSendToBack(xQueue, &sample, pdMS_TO_TICKS(10));    // 满了最多等 10ms

// ---- 消费者任务 ----
int16_t got;
if (xQueueReceive(xQueue, &got, portMAX_DELAY) == pdPASS) {
    Process(got);    // 拷出来的是副本，随便用
}

// ---- 中断里：绝不阻塞 ----
BaseType_t woken = pdFALSE;
xQueueSendToBackFromISR(xQueue, &sample, &woken);
portYIELD_FROM_ISR(woken);   // 与信号量的中断交接同一套配平，见信号量一篇
```

三个顺手的变体：`xQueueSendToFront` 从队头插（LIFO，给紧急数据插队）；`xQueuePeek` 只看不取（读走最新值但留给别人）；`uxQueueMessagesWaiting` 查水位（健康监测、判断消费者有没有积压）。

队列深度是创建时定死的，没有"自动扩容"——深度拍小了高负载时发送方开始等甚至失败，拍大了白吃 RAM。定量做法：按"消费者最坏处理耗时 × 生产速率"算积压上界，再留一倍余量。

## 二、任务通知：不走中介的直达路线

![[frtos-communication-object.webp|四种通信对象对比（Mastering FreeRTOS Figure 76）：队列、信号量、事件组都要先创建中间对象、经它转交；任务通知由发送方直接写目标任务的内核标志，不经过任何中间对象]]

![[frtos-task-notification.webp|任务通知的内核存储（Mastering FreeRTOS Figure 77）：每个任务自带 Notification State（Pending / Not-pending）与 32 位 Notification Value，零额外创建]]

队列再好也有账单：创建要花堆内存，每次收发要过队列的锁和等待链表。任务通知把这笔账全省了——**每个任务生来就带一个通知状态和一个 32 位通知值**，发送方直接写目标任务的这块内核存储，没有中间对象。代价是方向单一：只能"点对点直达一个任务"。

两套 API 对应两种用法：

```c
// ---- 用法一：轻量信号量（模拟二值/计数） ----
xTaskNotifyGive(xConsumerHandle);                    // 通知值 +1
vTaskNotifyGiveFromISR(xConsumerHandle, &woken);     // 中断同样直达

ulTaskNotifyTake(pdTRUE,  portMAX_DELAY);  // 取走即清零 → 二值语义
ulTaskNotifyTake(pdFALSE, portMAX_DELAY);  // 取走减 1   → 计数语义

// ---- 用法二：带 32 位值的灵活通知 ----
xTaskNotify(xConsumerHandle, 0x03, eSetBits);        // 按位置 1，像事件组
xTaskNotify(xConsumerHandle, seq, eSetValueWithOverwrite); // 直接覆写
uint32_t value;
xTaskNotifyWait(0, 0, &value, portMAX_DELAY);        // 等 Pending 并取回值
```

官方手册给的实测参考：任务通知比信号量**快约 45%**，且零额外 RAM。所以"中断叫醒一个任务"这种最高频的模式，官方推荐优先用通知而不是二值信号量——语义完全等价，开销低一截。

但直达路线的边界要记牢：

| 限制 | 后果 | 该换什么 |
| --- | --- | --- |
| 只能发给一个指定任务 | 广播、多消费者做不到 | 事件组（xEventGroupSetBits） |
| 发送方需要目标任务句柄 | 句柄没建好就没法发 | 队列（谁听谁取，发送方匿名） |
| 数据只有一个 32 位值 | 传结构体、不定长数据不行 | 队列 |
| 通知状态只有一位 | 没取走时连发两次会"合并" | 计数语义或队列 |

## 三、优先级反转：低优先级挡了高优先级的路

![[frtos-priority-inversion.webp|优先级反转时间线（Mastering FreeRTOS Figure 66）：LP 持锁进临界区，HP 请求同一把锁被阻塞；MP 与锁毫无关系，却因抢占 LP 而实际插到了 HP 前面执行]]

[[freertos-config-tasks|调度器一篇]]的规则是"高优先级永远先跑"，那高优先级任务怎么会卡在低优先级任务手里？时间线四步看懂：

1. **LP**（低）拿到互斥锁，进了临界区
2. **HP**（高）就绪，抢占 LP；接着请求同一把锁 → 锁被占，HP 阻塞
3. **MP**（中）就绪。MP 优先级高于 LP，直接抢走 CPU——此刻真实的执行优先级成了 **MP > LP > HP**：HP 在等 LP 手里的锁，而 LP 连 CPU 都拿不到
4. MP 跑完、LP 才得以跑完临界区放锁，HP 终于被唤醒

荒谬之处在第 3 步：MP 和那把锁**毫无关系**，却实实在在插到了全系统最高优先级任务前面。更糟的是，如果 MP 有一整串（定时器、日志、通信轮询轮流就绪），LP 可能长期拿不到 CPU，HP 被无限期拖着——这叫**无界优先级反转**，1997 年火星探路者号在火星上反复重启，根因就是它。

把保护资源的二值信号量换成互斥锁，问题不解决——反转照旧，因为二值信号量不带解药。解药在下一节。

## 四、优先级继承：临时提权，用完归还

![[frtos-priority-inheritance.webp|优先级继承时间线（Mastering FreeRTOS Figure 67）：HP 阻塞在 LP 持有的互斥锁上的瞬间，调度器把 LP 提到 HP 的优先级；MP 再也插不进队，LP 跑完临界区放锁、跌回原优先级，HP 立即接管]]

互斥锁与二值信号量的本质区别就一条：**互斥锁带优先级继承**。规则一句话——持有互斥锁的任务，会被临时提升到"正在等这把锁的任务里最高的那个"的优先级。

对照上一节的时间线：第 2 步 HP 阻塞的瞬间，LP 被提到 HP 的优先级；第 3 步 MP 再就绪也抢不走 CPU（同级不抢占，何况 LP 正带着 HP 的优先级跑临界区）；LP 放锁，优先级立刻还原，HP 接管。**反转从"无界"变成"有界"**——HP 最坏也只等一个临界区的长度，而这个长度是写代码的人自己控制的。

三条使用纪律：

* **Take 和 Give 必须同一个任务成对出现**——锁是"谁进谁出"的钥匙，不是接力棒
* **互斥锁禁止在中断里用**：继承机制要改任务优先级，中断不是任务，没有优先级可提。中断里要同步就回信号量/任务通知
* **临界区尽量短**：继承只是止损，持锁时间本身才是债务。锁里别等 I/O、别 printf、别 vTaskDelay

锁套锁会触发递归继承（A 等 B 的锁、B 等 C 的锁，层层上提），FreeRTOS 处理得了，但人脑处理不了——设计上就别嵌套。

## 五、选型速查

| 机制 | 带数据 | 保护共享资源 | 中断可用 | 优先级继承 | 相对开销 |
| --- | --- | --- | --- | --- | --- |
| 队列 | ✅ 拷贝任意定长 | ❌ | ✅ FromISR | ❌ | 中 |
| 二值信号量 | ❌ | ⚠️ 别这么用 | ✅ | ❌ | 中 |
| 计数信号量 | ❌（计数即数据） | ❌ | ✅ | ❌ | 中 |
| 互斥锁 | ❌ | ✅ 专用 | ❌ | ✅ | 中 |
| 任务通知 | 32 位值 | ❌ | ✅ | ❌ | **最低** |
| 事件组 | ❌（位标志） | ❌ | ✅ | ❌ | 中 |

选型顺序一句话：**先问要不要带数据**——带结构体/流就用队列；只是打招呼且收件人唯一，任务通知；保护共享资源，互斥锁；要广播给一群任务，事件组；管理资源池计数，计数信号量。

## 六、常见问题与注意事项

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 队列收到的数据"自己变了" | 传的是指针，源缓冲已被复用 | 传值；确要传指针就用缓冲池并约定所有权转移 |
| 高优先级任务偶发卡顿几十毫秒 | 无界优先级反转 | 资源保护换互斥锁，检查锁内是否干了慢活 |
| 互斥锁 Give 无效甚至断言 | Take/Give 不在同一任务，或在中断里用了 | 同任务成对；中断改用信号量/通知交接 |
| 任务通知偶尔"少了一次" | 状态位唯一，未取走时连发合并 | 改计数语义 ulTaskNotifyTake(pdFALSE)，或换队列 |
| 中断里队列满、发送总失败 | FromISR 不能阻塞 | 加深度；或中断只置标志，任务侧搬运 |
| 消费任务永远收不到广播 | 任务通知点对点，别的任务不在收件范围 | 事件组广播 |
| 想在定时器回调里发队列 | 回调上下文不许阻塞 | 用带超时 0 的发送，或 xTimerPendFunctionCall 转交 |

## 总结

队列用拷贝换来发送方与接收方的彻底解耦，深度按积压上界定；任务通知砍掉中间对象，点对点的同步首选它；互斥锁的优先级继承把反转从无界压到有界，代价是必须同任务成对、中断禁用。三件事串起来正好是 FreeRTOS 任务协作的进阶地图：**数据走队列，信号走直达，共享走带继承的钥匙**。往上接 [[freertos-config-tasks|任务调度]] 的优先级模型，往旁接 [[freertos-semaphore-callback|信号量家族]]，往下接 [[mcu-dma]]/[[mcu-can]] 里中断到任务的数据交接——每一处"ISR 里别做业务，拷走数据叫醒任务"，用的都是这页的套路。

> *数据走管道，信号走直达，共享走钥匙。* —— Iustitiae
